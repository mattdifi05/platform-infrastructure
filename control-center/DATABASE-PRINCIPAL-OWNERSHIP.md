# Database Principal Ownership

## Invariant

Application database principals are generated by the Control Center and are never accepted from a browser or API payload. A principal can be created, rotated, granted or removed only when an authoritative registry entry binds the exact principal to one project, engine and database resource.

The generated name is deterministic and project-scoped:

```text
pi_<engine>_<project-prefix>_<resource-hash>
```

The resource hash includes engine, project ID and database name. Names remain within the conservative MariaDB/PostgreSQL identifier limit.

## Registry

`PROJECT_DATABASE_PRINCIPALS_FILE` stores version 1 bindings in `projects-portal/state/database-principals.json`.

Each binding contains:

- database ID, project ID, engine and physical database name;
- generated principal name;
- ownership contract version;
- `reserved`, `active`, `migration-required` or `retired` state;
- non-secret timestamps.

Unreadable registry or database state fails closed. Both files are written with mode `0600` through atomic same-directory rename.

## Provisioning

Provisioning performs these checks before a privileged database command:

1. reject protected system databases;
2. reject every caller-supplied principal;
3. generate and reserve the exact principal binding;
4. inspect the database catalog;
5. reject an existing database or principal instead of adopting or altering it;
6. create a new principal and grant only the target database;
7. activate the binding only after successful provisioning.

The MariaDB and PostgreSQL provisioning paths contain no `ALTER USER`, `ALTER ROLE`, `IF NOT EXISTS` adoption or owner reassignment fallback.

## Credential rotation

Rotation is a separate path. It requires an active exact binding, an existing database owned by that principal, and a catalog principal without superuser, role-creation, database-creation, replication, bypass-RLS, global-admin or grant-option capabilities. A missing, foreign, reserved or privileged binding is rejected before credential mutation.

## Existing resources

Existing principals are never auto-adopted or rewritten by the platform. Any
manual ownership change requires its own reviewed maintenance procedure,
current backup/restore evidence and application-specific verification.

## Verification

`scripts/database-ownership-sandbox-test.sh` creates disposable, pinned MariaDB and PostgreSQL containers. It proves foreign principal collisions are rejected without database creation, exact bindings can provision and rotate credentials, foreign binding tampering cannot rotate, metadata/audit files contain no plaintext credential, and no platform database is contacted.

## Rollout gate

Live registry creation, principal creation, grants, credential changes and application cutover remain blocked. They require an approved maintenance window, fresh backup/restore evidence, application-specific dual-credential rollout and the later destructive-operation gate.
