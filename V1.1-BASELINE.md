## Cohort 4 candidate: measured Control Center preload coordination

The candidate retains the existing four-worker initial preload and its
all-pages-before-reveal contract. After the initial reveal, navigation-driven
refreshes are instead scheduled after a 200-ms quiet window with one
speculative worker. A real foreground navigation cancels both the queued quiet
window and any active speculative fetches, so foreground work never competes
with the preloader. After either foreground success or failure the background
preload is scheduled again; a failed request therefore cannot leave the cache
permanently partial.

This is a client-only change. It does not alter server routes, authorization,
passkey handling, PostgreSQL, Redis, project discovery, routing, Compose,
networks, volumes, secrets or persistent data. The existing Control Center
suite remains 94 tests; syntax validation, diff validation and all 94 tests
pass without adding a new test framework. Acceptance still requires exact-main
CI, a one-container rollout, a real authenticated Chrome exercise, absence of
new `499` responses during controlled navigation and before/after request and
latency evidence.

The first post-merge browser exercise rejected the idle-callback variant: 40
cached page changes were fast (6.9/14.3 ms p50/p95), but idle callbacks started
speculative work in the short gaps and seven requests were then aborted by the
next foreground navigation. The accepted candidate therefore removes that
branch and uses the single 200-ms quiet-window path above. This is both smaller
and directly testable against the observed contention.
